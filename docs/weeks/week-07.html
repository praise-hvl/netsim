Many cores on the board

Your computer runs programs, takes turns and handles interrupts. These steps put all of it on the board, on 1 to 8 cores: one lane per core, the scheduler's moves, and interrupts arriving. Do them at home after weeks 5 and 6 (the Build tab lists anything still open first). Monday 16 Nov is a check-in: bring what's stuck, show where you are, and I introduce many cores.

How each step works

The steps are grouped into components, the parts of your computer. Each one starts with what it is and what it will do, and ends by showing it working. The Build tab walks you through them in order.

  1. Read the idea (2-3 lines).
  2. Press Send to the agent, then read what it changed in the diff. Keep only what you can explain.
  3. When the tab says the step's tests pass, press Commit it, then Next step.
  4. Check you can answer the step's Ask in your own words: I use those questions in explain-it-back.

If a step fails, read its Stuck? line first. Push from the app whenever you stop. The Build tab remembers where you are: open it again and it shows your next step.

Getting help between classes

Post in the class chat: the step's number, and the first line of the failing test (or what the agent said). I answer there, and anyone who's past that step can help too. Mondays are check-ins: bring what's stuck.

Component 1 · Many cores on the board

The board shows every core: one lane each, the scheduler moving programs between them, and interrupts arriving. When it's done, you can watch your computer on 1 to 8 cores.

When it works: on the Board, press play on 2 cores and then 8: one lane per core, with moves and interrupts shown.
Check: npx vitest run tests/week-07/board-cores.test.ts

Design notes
PartWhat it shows
Lanesone per core, top to bottom, inside the CPU area, never overlapping
A core's laneyour core view: its steps, program and PC
Movesa program whose core changed since the last tick: landed, left or switched
"raised"an interrupt packet on the bus this tick, from its device
"taken"a core that started a handler this tick (it wasn't in one a tick ago)

On 2 cores and on 8 cores, the programs end with the same memory: a program's result doesn't depend on which core ran it.

Step 1 · One lane per core

The CPU area is split into one lane per core, top to bottom: every lane inside the area, none overlapping, for any count from 1 to 8.

Use this approach: split the area's height evenly by the count, one rect per core from top to
bottom, with a small gap between lanes.

Step 2 · The scheduler's moves

Compare which core each program is on between the last tick and this one. Every program whose core changed is a move: it landed, left, or switched.

Use this approach: for each process in this frame, compare its core with that process's core in the
previous frame, and list it when they differ.

Step 3 · Interrupts arriving

Two kinds of marker: "raised" for each interrupt packet on the bus this tick, and "taken" for each core that started a handler this tick (it wasn't in one a tick ago).

Use this approach: a raised marker for each irq packet this tick, and a taken marker for each core
in a handler now that wasn't in one in the previous frame.
