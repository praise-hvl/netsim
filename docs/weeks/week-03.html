Goals

  • Hardware idea: a memory access is a request and a reply across a shared bus, in step with the clock. Memory is byte-addressable (0x000–0x3FF), and an address outside it is a faultA reply that says a request failed and why, for example OUT_OF_RANGE for an address memory doesn't have. It replaces the normal reply, so the asker always hears back.. The clock only moves on when every request of the tick has its reply.
  • Software idea: two programs talking over a WebSocketA connection between two programs that stays open, so either side can send a message at any time. Every NetSim part keeps one open to the bus. with JSON messages; a handshake (hello → welcome); validating at the boundary with a schemaA description of what a valid message looks like: which fields, of which types. NetSim's is messageSchema, written with the zod library; it checks every message that arrives.; request/response correlation (id and replyToOn a reply, the id of the request it answers. It's how a requester matches each reply to its request, like a ticket number.); a pure function (memory) behind a thin shell.
  • On the board: the memory grid with cells lighting up on a read and a write, and packets travelling the bus wires: questions first, then answers. Your design from week 2, running.

What the code looks like (shape only)

return new Promise((resolve, reject) => {
  socket.addEventListener("open", () => socket.send(JSON.stringify(hello)), { once: true });
  socket.addEventListener("message", onMessage);  // resolve(welcome) or reject(error)
  socket.addEventListener("error", () => reject(new Error("could not reach the bus")));
});

A PromiseA value that isn't ready yet. handshake() and request() return one; await waits for it to resolve (the welcome or the reply) or reject (an error). lets the caller write const welcome = await handshake(...) and read the sequence top to bottom. And why a Map for request()? Two requests can be in flight at once, and replies can come back in any order.
