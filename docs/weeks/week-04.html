The CPU

Your bus and memory work. Today you design the part that uses them: a CPU core that fetches an instruction from memory, decodes it and executes it, one clock tick at a time. Then you build its first piece.

This class moved into week 5. We do the design and decode() together with the build, in one class: go to Week 5's page for the class and the take-home. This page stays as reference, and decode and encode keep their cards in this week's Code tab.

The hour has two halves. Design (30 min): the parts of your note next week's build needs. Build (30 min): decode(), which turns 4 bytes into an instruction, coded together. Next week you build the rest: a CPU that runs real programs, on screen.

The design half is yours alone; the build half is coded together on my shared screen.

Goals

  • Hardware idea: fetch–decode–execute. A program counter (PC) says where the next instruction is; registers (R0–R3, one byte each) hold the values being worked on; flags (zero, carry) remember facts about the last result. Every instruction is exactly 4 bytes with an agreed encoding. Memory has latency: a fetch costs a tick of waiting, so a LOAD takes one tick more than an ADD.
  • OS idea: the core is a finite state machine that only changes on the clock edge. Replies that arrive during a tick are latchedCaptured and held until the next tick: the reply arrives during tick 41, but the CPU only uses it in tick 42. and used on the next one, like a flip-flopA one-bit storage circuit that takes in a new value only at the clock edge. It's why hardware changes on ticks, not in between..
  • Design idea: a state machine is easiest to design as a table (from, event, to, what it does), and easiest to explain as a storyboard (what you'd see on each tick).
  • Software idea: decoding is a pure function: bytes in, an instruction (or an error) out. Every way the input can be wrong is an answer, never a crash.
